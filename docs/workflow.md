# §0. 결정 게이트 — 코드 돌리기 전에 4개를 먼저 확정 ★

> v1에서 미뤄둔 결정 4개. 여기서 정한 값을 `코드/00_config.py` 와 `코드/00_config.R` 에 **딱 한 번** 반영하면 전 스크립트가 따라온다. 상세 근거는 위키 `[[Phase2-결정대기]]`.

### ① EP(유럽) 처리방안 — 이번 논문의 핵심 ★★

**문제:** v1은 유럽(EP) 비중이 **1.4%**로 극소라 "유럽은 일반화 주의"라고 발을 뺐다. 원인은 원산지(Origin_Country)를 *최초 우선권 번호 앞 2글자*로 잡는데, 유럽 출원은 `EP`거나 `DE/FR/GB` 등 회원국 코드로 흩어져 대부분 EP로 안 잡혔기 때문.

**해결(권장): `EUROPE_MODE = "aggregate"`** — EPO 회원국 코드(DE·FR·GB·NL·CH·SE…)와 `EP`를 **하나의 '유럽(EP) 블록'으로 합친다.** 그러면 유럽 출원이 제대로 집계돼 미국·중국·일본·한국과 어깨를 나란히 하는 5번째 분석 단위가 된다.

| 옵션 | 의미 | 결과 |
|---|---|---|
| **`aggregate` (권장)** | EPO 회원국+EP → 'EP' 블록 통합 | 유럽이 실질 분석 가능해짐 (≈ 두 자릿수 %) |
| `strict` | v1 그대로, literal 'EP'만 | 유럽 과소대표 유지(1.4%) |
| `exclude` | 유럽 제외, 4개국만 | 유럽 분석 포기 |

➡️ **`00_config.py`의 `EUROPE_MODE` = `"aggregate"` 로 두고 시작.** (회원국 목록은 `EUROPE_CODES`에 이미 정의됨. 원하면 가감)
➡️ 위키 `[[EP처리방안]]`을 `status: confirmed`로 바꾸고 채택안 기록.

> 🔎 **검증 포인트:** `01` 실행 후 콘솔의 "EP(유럽) 비중" 출력과 `08`의 EDA_01 그림에서 EP 막대를 꼭 확인. 한 자릿수 초반이면 회원국 코드가 우선권에 안 잡힌 것 → `EUROPE_CODES` 점검.

### ② 2025·2026년 데이터 포함 여부

**문제:** 특허는 출원~공개까지 ~18개월 블라인드 → 최근 연도 과소추정. Gompertz·TLC는 시점 수(자유도)에 민감.
**권장:** `END_YEAR = 2025`로 **포함하되**, 논문에 *publication lag* 각주를 단다. 보수적으로 가려면 `2024`.
➡️ `00_config.py` `END_YEAR`, `00_config.R` `YEAR_END` **두 곳을 같은 값으로.** 위키 `[[2025년데이터포함]]` 확정.

### ③ 시드 재선별

**현황:** v1은 시드 157 / 안티시드 443 (머튼 6대 금융기능 기반).
**권장:** 방법(피인용 상위 + LLM 분류)은 유지. **개수는 자동결정** — 유럽 데이터에선 157/443에 맞출 필요 없음. 시드 분포에 유럽 출원이 너무 적으면 §3에서 유럽 시드를 의도적으로 보강.
➡️ 위키 `[[시드재선별]]` 확정.

### ④ K(토픽 수) 재탐색

**권장: K=20 유지.** 바꾸면 R 전 코드의 `1:20` 루프·길이20 라벨 벡터를 전부 고쳐야 함(작업량 큼). 유지가 현실적이고 v1과 비교도 쉬움.

# §1. Raw 데이터 수집 (The Lens, IP5 + 유럽)

> 목표: v1과 **같은 검색식·같은 컬럼 스키마**로, 기간만 갱신해 유럽이 잘 잡히도록 IP5 전체를 받는다.

### 1-1. 검색 범위
- **DB:** The Lens (lens.org) — Patents
- **관할(Jurisdiction):** IP5 = **US · EP · CN · JP · KR** (EP 포함이 핵심)
- **기간:** 출원일 기준 §0-② 결정 반영 (예: 2019-01-01 ~ 2025-12-31). 시드용은 v1과 동일하게 ~2026-02-01까지 넉넉히.
- **주제:** 핀테크 6대 기능틀 → 위키 `[[핀테크정의-기능분류]]`, `[[시드선정방법론]]`

### 1-2. 검색식 (v1 재사용)
v1 원본 쿼리: `6_데이터/the lens 쿼리.txt`. **CPC AND (title/abstract 키워드)** 구조를 그대로 쓴다.
- 분류별 CPC 매핑 예: 결제 = `G06Q20` 계열 + `G07F` + `H04L9`; RegTech = `G06Q40` AND (`G06F21`/`H04L63`)
- 7대 분류로 각각 검색 → CSV로 내려받아 합침. (④ 디지털뱅킹 쿼리는 v1처럼 보류 가능)

### 1-3. 다운로드 컬럼 (★스키마 고정)
아래 컬럼이 **반드시** 포함돼야 한다(이름까지 동일). `00_config.py` `COL_*`가 이 이름에 의존:
```
Title, Abstract, Jurisdiction, Priority Numbers, Earliest Priority Date,
Application Date, Publication Year, Cited by Patent Count,
Extended Family Members, Extended Family Size, Applicants, Lens ID
```

### 1-4. 통합

- **판정 = Gemini**, (필요시) **번역 = GPT**. (도구는 바꿔도 됨. 핵심은 일관된 룰)

### 3-2. Gemini 프롬프트 (v1 룰 그대로)
1. 역할 부여 + FSB/BCBS 핀테크 정의 + 운영범위 3단계(Narrow/Core+/Broad) + 7대 분류 가이드 주입
2. 명칭+초록을 **5건씩** 전달 → 각 건의 시드 적합 여부 + 7분류 중 적합 분류 판단
3. 답변 양식: `특허번호 / 명칭 / 시드 판정[적합·부적합] / 분류 상위 3순위 / 핵심근거(기술 실질성·기준점 역할)`

**판정 룰 (verbatim):**
- **적합** = 시드 적합 + 분류 1등 → `fintech = TRUE`
- **보류** = 시드 적합 + 분류 2등 → 보통 TRUE 편입(판단)
- **부적합** = 시드 부적합 + 분류 3등 & OUT → **안티시드** `fintech = FALSE`(또는 `OUT`)

> ⚠️ 명칭 기반 함정: "P2P/Peer-to-peer"가 가장 위험(대부분 서버통신·파일공유 IT). 제목에 `InsurTech/RegTech/DeFi/Neobank/Robo-advisor`면 1순위 시드.
> 🇪🇺 **유럽 보강:** 시드 중 유럽 출원이 거의 없으면, 유럽 출원인(예: SAP, Adyen, Klarna, Wise, N26, Ingenico 등) 특허를 시드 후보에 의도적으로 추가해 임베딩 공간에서 유럽이 대표되게 한다.
